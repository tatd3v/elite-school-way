# Project Notes for AI Agents

Elite Way School — Ballroom event registration SPA. Preact + Vite + Tailwind frontend,
Google Sheets/Apps Script backend (no traditional server/DB).

## Tech stack & structure
- **Framework**: Preact (`preact/hooks`, `preact/compat` for `createPortal`), not React — imports must come from `preact/hooks` / `preact/compat`, not `react`.
- **Build**: Vite (`npm run dev`, `npm run build`, `npm run preview`).
- **Styling**: Tailwind CSS with a custom design-token config (colors like `on-surface`, `surface-container`, font sizes like `text-display-lg`, spacing like `px-margin-mobile`). `@tailwind`/`@apply` warnings from generic CSS linters in `src/index.css` are expected/harmless — Tailwind processes them at build time.
- **Routing**: a small hand-rolled router (`src/components/Router.jsx`) — matches `window.location.pathname` against a routes array and re-renders on `popstate`. Routes: `/` (public site), `/login` (admin login → dashboard once authenticated), `*` (falls back to `/`). Note the `preact-router` package is listed in `package.json` but is **not actually used anywhere** — don't assume it's wired up.
- **Verification**: `npm run build` (or `npx vite build`) is the fast sanity check used throughout this project's history. Also available: `npm run lint`, `npm run test`.
- **Hosting**: Vercel (see `vercel.json` — SPA rewrite of all paths to `index.html`, needed since routing is client-side). The docs previously said Netlify; that's stale — there's no Netlify config in the repo.
- Run shell commands via `wsl -e bash -lc "cd ~/elite-school-way && ..."` — the repo is accessed through a WSL UNC path from Windows.
- **UNC path read/write caching gotcha**: file read/edit tools operating on `\\wsl.localhost\...\elite-school-way\...` paths have, more than once in this project's history, returned/"successfully written" content that did **not** match what was actually on disk (verified by directly `cat`-ing the same file through `wsl -e bash -lc`) — in both directions (stale reads showing old content, and edits reporting success while the real file kept its old content). If a change doesn't seem to take effect, or output looks inconsistent with a previous step, don't trust the read/edit tool alone — verify with `wsl -e bash -lc "cat ~/elite-school-way/path/to/file"` before concluding there's a code bug. If a write genuinely didn't persist, rewriting the file (e.g. via the `write` tool) and re-verifying with `cat` has resolved it.

## Backend: Google Apps Script (`google-apps-script.md`)
This file is the **source of truth** for the backend script — it must be manually copy-pasted into the Google Apps Script editor (Extensions > Apps Script on the Google Sheet) and does not deploy automatically.

Key sheets (auto-created lazily on first use, not up front):
- **Registrations** — form submissions (`initializeSheet`)
- **Users** (formerly "Admins") — admin/viewer accounts (`initializeAdminsSheet`), columns: Email, Password Hash (SHA-256), Role, Name
- **Staff** — staff/faculty directory (`initializeStaffSheet`), columns: Name, Role, Bio, Photo URL, Social Links, Display Order, Is Visible

### Critical Apps Script gotchas (already hit and fixed multiple times — don't repeat)
1. **`ContentService` has NO `setHeader`/`addHeader` API.** Do not add CORS headers this way — it throws `TypeError: ... setHeader is not a function` at runtime (only surfaces when the deployed endpoint is actually hit, e.g. via `curl`, not from a code review). `createJsonResponse` must stay a plain `ContentService.createTextOutput(...).setMimeType(...)` with no header calls.
2. **CORS is handled by avoiding it entirely**, not by fixing headers:
   - Reads (`getRegistrations`, `getStaff`, `login`) go through **JSONP** (`src/utils/jsonp.js`, shared by `dashboardService.js` and `authService.js`) — loads response via a `<script>` tag, which sidesteps CORS. Apps Script's `doGet` supports a `callback` param for this.
   - Writes (form submit, staff update/delete/toggle) use `fetch` with `mode: 'no-cors'` and `Content-Type: 'text/plain'` (not `application/json`) to avoid triggering a preflight `OPTIONS` request, which Apps Script can't answer properly anyway.
   - Login (`AUTH_CONFIG.LOGIN_ACTION`) is sent as a JSONP **GET** (email/password as query params) — note this means credentials are visible in browser history/server logs; acceptable for this project's low-stakes admin demo but flagged as a real trade-off.
3. **Editing the Apps Script code and saving does NOT update the live deployment.** You must explicitly go to **Deploy → Manage deployments → (pencil/edit icon) → Version: "New version" → Deploy**. Forgetting this step is the single most common cause of "it still doesn't work" — always ask/verify this was done when debugging a script behavior change, and it can be confirmed by `curl`-ing the deployed URL directly and reading the raw HTML error (Apps Script returns error details in a simple `<div class="errorMessage">` on failure, e.g. `TypeError: ... (línea N, archivo "Code")`), which reveals the exact deployed line number — compare against the current script to check if the deployment is stale.
   - Concretely hit this after commit `b130873` renamed the registrations sheet's `categories` field to `entryType` in `google-apps-script.md` — the live deployment was never redeployed, so `getRegistrations()` still returns `categories` in production, making `registrations.integration.test.js`'s `entryType` assertion fail. This is a deployment problem, not a test/code bug — fix by redeploying, not by changing the field name back.
4. Deployment must be **Execute as: Me**, **Who has access: Anyone**.
5. **`entryType` stores a numeric price, not the category label.** `RegistrationModal.jsx`'s radio options are full label strings (e.g. `'General — $20.000'`), but `formSubmit.js` strips everything except the digits (`formData.entryType.replace(/\D/g, '')`) and sends the resulting `Number` (e.g. `20000`) — or `'N/A'` if no digits are found. The backend's own registration-submission handler does the same digit-extraction again as a second safety net. So the Registrations sheet's "Entrada" column holds a price like `20000`/`15000`, never the literal label — don't write tests or code that expect the raw label string to round-trip.

## Roles (Users/Admins sheet)
- `admin` role → full dashboard access (actions menu, edit/delete participants, manage staff).

## Known fragile areas / external dependencies
- **Staff photo hosting**: Google Drive share links and Imgur album links do NOT work as direct `<img src>` — they need direct file links (`i.imgur.com/...` for Imgur; Drive requires "Anyone with the link" sharing + a direct embed format, and even then Drive hotlinking has been unreliable/rate-limited by Google). `src/utils/driveImage.js`'s `getDriveImageCandidates()` has a best-effort multi-candidate fallback chain for Drive links, tried in order by `StaffMemberCard.jsx`'s `onError` handler — the raw share link (`.../view?usp=...`) is deliberately **not** one of the candidates (it always fails as an `<img src>`, so including it just wastes the first attempt); candidates start directly with `thumbnail?...&sz=` variants (multiple sizes), then `uc?id=`/`uc?export=download`/`uc?export=view`, then `lh3.googleusercontent.com/d/`. Recommend migrating to Imgur/Cloudinary/self-hosted images long-term regardless.
- **Old Android WebView compatibility**: avoid the CSS `aspect-ratio` property (unsupported on older Android WebViews — collapses container to 0 height, making content invisible). Use the classic padding-percentage trick instead (`position: relative` + `padding-top: X%` + absolutely positioned child) — see `StaffMemberCard.jsx`.
- **Mobile horizontal overflow**: `html`/`body` in `src/index.css` have `overflow-x: hidden` as a safety net. When adding new large headings, always step down font size responsively (see `Hero.jsx`'s `text-3xl md:text-display-lg-mobile lg:text-display-lg` pattern) rather than using bare `text-display-lg`, since 56px headings can overflow narrow viewports.
- **Sticky mobile headers vs. `backdrop-filter` cards**: `.glass-panel`/`.glass-card` (mobile participant/staff cards) use `backdrop-filter: blur(...)` with a translucent background. Mobile browsers sometimes promote `backdrop-filter` elements to their own compositing layer that ignores normal z-index stacking against `position: sticky`, letting card content bleed through the sticky header while scrolling. Fix: give the sticky header `isolate` + `[transform:translateZ(0)]` + a higher `z-index` (30) to force it onto its own layer above the cards — see the mobile header wrappers in `AdminDashboard.jsx` and `StaffManagementSection.jsx`.
- **Independent per-tab mobile scroll containers**: `AdminDashboard`'s `<main>` does NOT scroll itself on mobile (`overflow-hidden`, not `overflow-y-auto`) — if it did, its `scrollTop` would persist across tab switches (since `main` is one persistent DOM node shared by both tabs), making the Participantes and Staff lists appear to "scroll together"/carry over each other's position. Instead, each tab's own mobile card list div owns its own bounded `flex-1 min-h-0 overflow-y-auto` scroll region (`AdminDashboard.jsx`'s Participantes card list, `StaffManagementSection.jsx`'s Staff card list). Because each tab's content is conditionally rendered/unmounted, switching tabs always mounts a fresh scroll container at `scrollTop: 0` — scroll state can't leak between the two views. The mobile "Cargar más" button must live *inside* this scrollable div (as the last child, after the `.map()`) so it scrolls with the list instead of sitting outside it as a static element.
- **Vitest integration tests must run sequentially**: `appsScript.integration.test.js` and `registrations.integration.test.js` both hit the SAME live Google Apps Script deployment. Vitest runs test *files* in parallel by default, and concurrent writes/reads against the same deployment cause contention that makes requests time out (observed as ~6 cascading failures in the Staff test suite). `vitest.config.js` sets `fileParallelism: false` to fix this — do not remove that setting to "speed up" tests without re-verifying the full suite passes reliably (run it 2-3 times; the flakiness is intermittent).
- **Nav anchors must target the specific sub-block, not a shared wrapping `<section>`**: `RulesSection.jsx` renders both `DressCode` and `CodeOfConduct` inside one outer `<section>`. Putting a nav anchor `id` on that outer section (as `#rules` once was) means the anchor jump lands wherever the section *starts* — which visually looks like DressCode, not the conduct rules further down. Each nav target needs its own `id` directly wrapping the specific block it should scroll to (`#dresscode` around `<DressCode />`, `#rules` around `<CodeOfConduct />`), each with `scroll-mt-20` so the fixed header (`h-16`) doesn't overlap/hide the block's own heading when jumped to directly.

## Theming (light/dark + scoped admin palette)
- Light-mode values live in `tailwind.config.js`; dark-mode values are **class-override rules** in `src/index.css` (`.dark .bg-primary { ... !important }`), not `dark:` variants in components.
- The admin dashboard uses its **own light palette** (crimson `#b91d20` primary, brass `#765b00` secondary, warm outlines), scoped via `.admin-theme` rules in `src/index.css`. `AdminDashboard.jsx` adds/removes `admin-theme` on `<html>` in a `useEffect` — on `<html>` and not the root div so `createPortal` modals/menus in `document.body` inherit it. The public landing page keeps the original navy/red branding.
- **Key gotcha:** Tailwind automatically derives state variants (`hover:`, `active:`, `focus:`, `group-hover:`) for these override rules from their **base** form — writing `.admin-theme .text-primary` also yields `.admin-theme .hover\:text-primary:hover`. So declare the base utility (including each opacity step like `.bg-secondary\/20`, which is a separate rule) and let Tailwind expand it, instead of hand-writing state selectors. `focus-within:` is the one variant it does **not** derive — that needs an explicit rule.
- `.admin-theme` rules intentionally omit `!important` so the `!important` dark-mode rules always win and dark mode stays unaffected.
- `.glass-panel` / `.glass-card` / `.linen-texture` are custom component classes in `src/index.css` with explicit light defaults and `.dark` overrides. When adding such a class, always define the light value too — a hardcoded dark value leaks into light mode (this caused navy cards/backgrounds on the light theme more than once).
- `ThemeToggle.jsx` is shared across `Header.jsx` (public site), `AdminDashboard.jsx`, `StaffManagementSection.jsx`, and `DashboardHeader.jsx`. Its button is a fixed `w-10 h-10` touch target with a `text-2xl` (24px, the standard Material Symbols default) icon — this is intentional and shared globally; don't special-case its size in just one usage, since that creates visual inconsistency across the app (this was fixed once already — the icon used to have no explicit size and rendered too small/inconsistently next to other header icons).

## Pagination
- **AdminDashboard (Participants) — desktop table**: Uses proper `currentPage`/`pageSize` pagination (state: `currentPage`, `pageSize`), sliced via `desktopVisibleParticipants = filteredParticipants.slice((currentPage - 1) * pageSize, currentPage * pageSize)`. `Filas` selector updates `pageSize` and resets to page 1. Page number buttons and previous/next chevrons navigate `currentPage`. Text shows `Mostrando {start}-{end} de {total}`.
- **AdminDashboard (Participants) — mobile card list**: Intentionally kept as a separate, simpler incremental "load more" pattern (state: `visibleCount`, initial `15`), fully independent of the desktop `currentPage`/`pageSize` above — `mobileVisibleParticipants = filteredParticipants.slice(0, visibleCount)`, grown by `15` per press via `handleLoadMore`/"Cargar más" button (`pb-32` + `scroll-mb-24` + `scrollIntoView` keep the button clear of the fixed `BottomNavigation`). Do not merge this into the desktop `currentPage` scheme without explicit approval — they were deliberately decoupled so fixing desktop pagination wouldn't change mobile UX.
- **StaffManagementSection (Staff) — desktop table**: Uses proper `currentPage`/`pageSize` pagination (state: `currentPage`, `pageSize`), sliced via `visibleStaff = sortedStaff.slice((currentPage - 1) * pageSize, currentPage * pageSize)`. Same `Filas`/page button/chevron/`Mostrando` conventions as Participants.
- **StaffManagementSection (Staff) — mobile card list**: Also decoupled into its own incremental "load more" pattern (state: `mobileVisibleCount`, initial `15`), independent of the desktop `currentPage`/`pageSize` — `mobileVisibleStaff = sortedStaff.slice(0, mobileVisibleCount)`, grown by `15` per press via `handleLoadMoreMobile`/"Cargar más" button, same `pb-32`/`scroll-mb-24`/`scrollIntoView` clearance treatment as Participants.

## Public site navigation (`Header.jsx`)
- Section links live in a single `NAV_LINKS` array (`#event`, `#staff`, `#categories`, `#dresscode`, `#rules`) shared by both the desktop `nav` and the mobile dropdown menu — add new section links there once, not in two places.
- Mobile (`md:hidden`) has a hamburger button that toggles a dropdown panel with the same links, plus an **"Inscríbete Ya!"** CTA button as the first item that calls `onOpenModal` (opens `RegistrationModal`) — this CTA is mobile-only by design, not part of `NAV_LINKS`/the desktop nav.
- The logo links to `/` and intercepts the click: always `preventDefault()`s, explicitly resets the URL to `/` via `history.pushState` (clearing any leftover section hash like `#rules` from a previous nav click — without this the address bar keeps the old hash even after scrolling away, making the click look like it did nothing), then smooth-scrolls to the top.
- `NAV_LINKS`/`Header.jsx`'s `handleNavClick` intercepts every section link click too: it scrolls to the target manually via `scrollIntoView` and then resets the URL back to a clean `/` via `history.pushState`, so the hash never actually shows up in the address bar after an in-page nav click.
- Anchor targets need `scroll-mt-20` to clear the fixed header — see the "Nav anchors" gotcha above.
- **Shareable deep links, independent of the "clean URL" behavior above**: `App.jsx`'s `HomePage` has a mount-time `useEffect` that reads `window.location.hash` once on initial load (not on later in-page nav clicks) and either `scrollIntoView`s the matching section, or — if the hash equals the dedicated `REGISTRATION_HASH` (`'#inscripcion'`) — opens the registration modal instead, since there's no DOM element to scroll to for a modal. `openModal`/`closeModal` push/clear that same hash via `history.pushState` so the modal itself becomes a shareable link (`tusitio.com/#inscripcion`), and a `popstate` listener keeps the modal in sync with the browser back/forward buttons. Don't confuse this with `Header.jsx`'s hash-cleaning behavior above — one is "hide the hash after an internal click", the other is "restore behavior from a hash present on first load".

## Public site section layout pattern (boxed sections + `ShareButton` + unified headers)
All top-level public sections (`Hero`, `EventDetails`, `StaffSection`, `Categories`, `RulesSection`, `FinalCTA`) follow the same structural conventions — match these when adding a new section or editing an existing one:
- **"Boxed" background on wide screens**: the background color, `max-w-*`, `mx-auto`, and horizontal padding (`px-margin-mobile md:px-margin-desktop`) must all live on the *same* top-level `<section>` element (most use `max-w-7xl`; `FinalCTA` also uses `max-w-7xl` on the section but nests an inner `max-w-2xl mx-auto text-center` div just to keep its CTA copy narrower). This is what makes each section render as a centered "card" with the page's true `bg-background` visible as gutters on screens wider than the max-width (~1280px) — putting the `max-w`/`mx-auto` only on an *inner* `<div>` while the background lives on the full-bleed outer `<section>` breaks this (it happened repeatedly while unifying `EventDetails.jsx`/`Categories.jsx`/`FinalCTA.jsx` — always double check both live on the same element).
- **Background color**: `bg-surface-container-low dark:bg-surface-container` on every section (this was unified from a mix of `bg-surface-container-high`/`bg-surface-container-lowest`/missing-dark-variant across sections — don't reintroduce per-section variance).
- **Vertical rhythm**: `py-12 md:py-section-gap-desktop` on every section (also previously unified — `StaffSection` used to be the odd one out with `py-12 md:py-16`).
- **Separator**: every section carries `border-b border-outline-variant/20` (same color/opacity everywhere) so adjacent sections show exactly one separating line — don't add a `border-t` on the *next* section too, or the line doubles/mismatches (this happened with `FinalCTA`'s old `border-t border-outline-variant/10`).
- **Section header**: pretitle + title + underline bar, centered — `<span className="text-secondary font-label-lg text-label-lg tracking-[0.4em] uppercase mb-2 block">` (pretitle) → `<h2/h3 className="font-display-lg text-3xl md:text-display-lg-mobile lg:text-display-lg text-primary uppercase leading-tight">` (title) → `<div className="w-24 h-1 bg-secondary mx-auto mt-4">` (underline), all wrapped in a `text-center` div. Originated in `StaffSection.jsx`, now mirrored in `EventDetails.jsx`, `Categories.jsx`, `DressCode.jsx` (both mobile/desktop variants), and `CodeOfConduct.jsx`.
- **`ShareButton.jsx`**: a reusable circular (`w-10 h-10 rounded-full`) share/copy-link button, `absolute top-4 right-4 md:top-6 md:right-6 z-10` inside each section's `relative`-positioned container (the section needing `relative` is easy to forget — the button silently mispositions relative to a further-up ancestor without it). Shares `${origin}${pathname}#${sectionId}` via the Web Share API, falling back to clipboard copy (shows a temporary `check` icon, 1.6s) and finally `prompt()`. Styling is glassmorphic and theme-aware for free: `hover:border-secondary hover:text-secondary` resolves to red in light mode / gold in dark mode purely from the existing `.dark .text-secondary`/`.dark .border-secondary` overrides in `index.css` — no extra `dark:` classes needed for that part. Present on `EventDetails`, `StaffSection`, `Categories`, `DressCode` (both variants), and `CodeOfConduct`; intentionally **not** on `Hero` or `FinalCTA` (both are CTA/banner-style, not "shareable content" sections).
- **`Hero.jsx` is the deliberate exception** to the boxed pattern above — it's a full-bleed viewport banner with its own background image + gradient overlay, not a `bg-surface-container-low` card. Its height is `min-h-[85vh] md:min-h-screen h-auto md:h-[90vh]`: note `min-height` wins over `height` in CSS whenever it specifies a *larger* value, so `md:min-h-screen` (100vh) is what actually forces full-viewport height on desktop even though `md:h-[90vh]` is also set — dropping the `md:min-h-screen` (e.g. while only trying to fix the *mobile* height) silently shrinks the desktop hero to a true 90vh, which looks "shrunk" compared to before. If you need to adjust Hero's height again, change the two breakpoints' values together and re-check both.

## Code Quality & Best Practices (Always Apply)
- **DRY (Don't Repeat Yourself)**: Extract repeated logic into reusable functions/utilities. Avoid duplicating code across components or services.
- **KISS (Keep It Simple, Stupid)**: Prefer simple, straightforward solutions over complex ones. Avoid over-engineering.
- **Naming**: Use clear, descriptive names for variables, functions, and components. Avoid abbreviations unless they're standard (e.g., `id`, `url`).

## SOLID Principles (Always Apply)
**S - Single Responsibility Principle**: Each class/function/component has ONE reason to change. If it does multiple things, split it.
  - ✅ `dashboardService.js` handles data fetching only
  - ✅ `AdminDashboard.jsx` handles UI state and layout only
  - ✅ `staffTestRunner.js` handles testing only
  - ❌ Don't mix business logic with UI rendering

**O - Open/Closed Principle**: Code should be open for extension, closed for modification. Use composition and abstraction.
  - ✅ Add new staff actions by extending `STAFF_CONFIG.ACTIONS`
  - ✅ Create new components by composing existing ones
  - ❌ Don't modify existing functions to add new features; extend them instead

**L - Liskov Substitution Principle**: Subtypes must be substitutable for their base types. Derived classes should not break the contract.
  - ✅ All staff members follow the same shape: `{ rowIndex, name, role, bio, photo, socialLinks, displayOrder, isVisible }`
  - ✅ All API responses follow consistent structure: `{ status, data, error }`
  - ❌ Don't return different shapes for the same function

**I - Interface Segregation Principle**: Clients should not depend on interfaces they don't use. Keep interfaces small and focused.
  - ✅ `dashboardService` exports only the methods needed by components
  - ✅ Test utilities (`staffTests`) expose only the functions users need
  - ❌ Don't force components to import/use functions they don't need

**D - Dependency Inversion Principle**: Depend on abstractions, not concrete implementations. Inject dependencies.
  - ✅ Components depend on `dashboardService` (abstraction), not directly on fetch/JSONP
  - ✅ Tests can mock `dashboardService` for unit testing
  - ❌ Don't hardcode API calls directly in components
